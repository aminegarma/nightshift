# Appendix B: PRD changes from the architecture (AP-1 to AP-20)

Part of the architecture hand-in (2026-11-15). Changes the architecture proposed to the PRD. The PRD update of 2026-11-15 adopted AP-1 to AP-8, refined by Amine's conflict decisions 1 to 7 and the remaining-point decisions (noted per row), and added AP-9 to AP-20. Change report: `prds/prd-nightshift-2026-10-28/update-notes-2026-11-15.md`. Process history: `.working/prd-change-queue.md`.

| AP-2 | **Adopted into the PRD 2026-11-15.** Approval confirmation (option B, pending feasibility and usability testing): passkey sign-in, Approve, an SMS from the cluster naming the action with a one-time code, enter the code (paste and auto-fill allowed), then a fresh passkey assertion over the decision fingerprint; the cluster checks that both bind to the same decision. As adopted (conflicts 3 and 4): permissions are classified by required authority and never used beyond their own validity; stale (from 1 h): customer-only safe ticks continue, permissions requiring Orvex authority pause (management policy, Orvex technical approval including approvals already received, Orvex side of last resort), so safe policy repairs' cutoff moves from 24 h to 1 h; expired (24 h): customer-only safe ticks continue within their own validity, delegations only for decisions already received, Orvex-authority permissions stop. | AP-6 | **Adopted into the PRD 2026-11-15.** **Code fixes: hosted first (replaces "in-cluster by default").** Hosted inference is the main v1 approach when the customer separately authorises sending the relevant source code to a trusted, zero-retention provider. An in-cluster model is also supported when suitable hardware exists and the customer wants code to stay in the cluster. If neither is available or authorised, code fixes are unavailable, while monitoring and catalogue-based repairs continue. The source-code consent stays separate from external-AI consent (PRIV-8) and stays off until the customer opts in | PRD 3.1 (scope bullet), FR-43 (title and body), FR-44 step 1, PRIV-6, Section 7 table ("the default for code fixes"), Section 10 item 7a; UX EXPERIENCE.md settings row "Source code (separate permission)" (currently "Code fixes need an in-cluster GPU") and the B6b consent wording | Round 4.1, Amine 2026-11-04 (after Danny, Exchange 3) |
| AP-7 | **Adopted into the PRD 2026-11-15.** **Bounded probation rollback inside the update authorisation.** A maintenance-policy update includes an exact, bounded rollback: back to the named previous signed release, only within the probation window, only when the probation check fails, and only if the release is marked rollback-safe. It preserves permissions, approvals and safety rules, and is recorded like any change (FR-33). Any other rollback stays under the rollback policy or approval (FR-47). As adopted (conflict 5): a security-update rollback needs an explicit advance customer policy covering the recovery version, the known vulnerability it reintroduces and the recovery limits; without it, Nightshift escalates urgently instead of rolling back automatically; any rollback is rollback-safe, recorded and followed by a plan to restore the security fix. Was: "(and a security update)" included in the bounded rollback | PRD FR-47 (routine and security updates), FR-32 table row "Roll back a verified update", FR-33 | Round 5.4 R2, Amine 2026-11-05 |
| AP-8 | **Adopted into the PRD 2026-11-15.** **Name the outbound paths that do not pass through the gateway.** SEC-8 says all data leaving the cluster passes through the gateway. The adopted design has three exceptions: the Fleet heartbeat sent by the independent checker on its own fixed-schema path (round 3.4), Flux pulling signed packages from the registry (5.2), and the optional EKS AWS poller calling the customer account's Describe APIs (3.3). Proposed: SEC-8 lists these as the only exceptions, each with its own destination allowlist, and every Nightshift pod gets default-deny egress. As adopted (conflicts 6 and 7, remaining points): the required channel is the Fleet service channel, carrying exactly the heartbeat with checkpoint, relay status statements and signed key lists, signed release, catalogue and model downloads, policy and roster updates and the fixed attention notice, each with exact permitted fields disclosed at onboarding ("minimal service metadata; no raw logs, secrets or application content"); the AWS poller is separately optional; the FR-12 signal goes under Fleet reports; every outbound flow is checked, with purpose-specific controls on the three paths (defined destinations, operations, request fields, authentication and limits), not automatically equivalent to the gateway, enforcement to verify | PRD SEC-8, PRIV-9; addendum "egress only through the gateway" | Round 9 reconcile (C-1), 2026-11-11; design adopted by Amine as D2 (AD-67); PRD change adopted 2026-11-15 |
