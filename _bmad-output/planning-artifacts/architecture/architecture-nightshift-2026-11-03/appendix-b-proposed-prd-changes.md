# Appendix B: Proposed PRD changes (AP-1 to AP-8)

Part of the architecture hand-in (2026-11-15). Changes the architecture proposes to the PRD; none is part of the PRD until a PRD update accepts it. Process history: `.working/prd-change-queue.md`.

| # | Proposed change | Affects | Source |
|---|---|---|---|
| AP-1 | Add a minimal audit checkpoint (`audit_seq`, `chain_head`, `checkpoint_time`, `audit_key_id`, `checkpoint_sig`; fixed schema, no text) to the required Fleet heartbeat. Onboarding explains the new fields and their purpose | PRD FR-6 (heartbeat fields), PRIV-9, NFR-4; UX onboarding channel screen | Round 2.3, Amine 2026-11-03 (`round2-trust-design.md`) |
| AP-2 | Approval confirmation (option B, pending feasibility and usability testing): passkey sign-in, Approve, an SMS from the cluster naming the action with a one-time code, enter the code (paste and auto-fill allowed), then a fresh passkey assertion over the decision fingerprint; the cluster checks that both bind to the same decision. Passkey-only fallback only where policy explicitly enables it, shown and recorded as reduced assurance; SMS failure never downgrades requirements. Applies to Orvex approvals and to the performer's "Start now" too. "I've done it" is an authenticated completion report (fresh passkey assertion over the report, no SMS step), not an approval, and stays reportable after the window ends. Plus a cluster-originated "You approved… Not you? Withdraw" notice | PRD FR-14 (approval steps), FR-13 (SMS), PRIV-3 allowlist for the SMS fields, PRIV-9 (SMS as part of notifications), SEC-7 (fallback setting); UX confirmation sheet and states (replaces the deferred finding "a request code against phishing") | Round 2.1 revised, Amine 2026-11-04 |
| AP-3 | "Sent — not yet effective in the cluster" until a signed cluster receipt arrives (the wording replaces "sent, not yet confirmed") | PRD FR-22 wording; UX state patterns | Round 2.2, Amine 2026-11-03 |
| AP-4 | Bounded offline validity for ticks, policies, rosters, delegations and channel permissions, with fresh / stale / expired tiers (stale: only safe ticked and safe policy repairs; expired: no automatic repairs) | PRD FR-22, FR-51, NFR-5; UX cluster status | Round 2.2, Amine 2026-11-03 |
| AP-5 | Documented reduced coverage: no automatic repair needing the Kubernetes API while the API is down; control-plane failures are reported and escalated to a person in v1 | PRD 3.1 or FR-20/FR-5 wording; failure catalogue | P6, Amine 2026-11-03 |
| AP-6 | **Code fixes: hosted first (replaces "in-cluster by default").** Hosted inference is the main v1 approach when the customer separately authorises sending the relevant source code to a trusted, zero-retention provider. An in-cluster model is also supported when suitable hardware exists and the customer wants code to stay in the cluster. If neither is available or authorised, code fixes are unavailable, while monitoring and catalogue-based repairs continue. The source-code consent stays separate from external-AI consent (PRIV-8) and stays off until the customer opts in | PRD 3.1 (scope bullet), FR-43 (title and body), FR-44 step 1, PRIV-6, Section 7 table ("the default for code fixes"), Section 10 item 7a; UX EXPERIENCE.md settings row "Source code (separate permission)" (currently "Code fixes need an in-cluster GPU") and the B6b consent wording | Round 4.1, Amine 2026-11-04 (after Danny, Exchange 3) |
| AP-7 | **Bounded probation rollback inside the update authorisation.** A maintenance-policy update (and a security update) includes an exact, bounded rollback: back to the named previous signed release, only within the probation window, only when the probation check fails, and only if the release is marked rollback-safe. It preserves permissions, approvals and safety rules, and is recorded like any change (FR-33). Any other rollback stays under the rollback policy or approval (FR-47) | PRD FR-47 (routine and security updates), FR-32 table row "Roll back a verified update", FR-33 | Round 5.4 R2, Amine 2026-11-05 |
| AP-8 | **Name the outbound paths that do not pass through the gateway.** SEC-8 says all data leaving the cluster passes through the gateway. The adopted design has three exceptions: the Fleet heartbeat sent by the independent checker on its own fixed-schema path (round 3.4), Flux pulling signed packages from the registry (5.2), and the optional EKS AWS poller calling the customer account's Describe APIs (3.3). Proposed: SEC-8 lists these as the only exceptions, each with its own destination allowlist, and every Nightshift pod gets default-deny egress | PRD SEC-8, PRIV-9; addendum "egress only through the gateway" | Round 9 reconcile (C-1), 2026-11-11; design adopted by Amine as D2 (AD-67), PRD change still pending |

**Note:** within AP-2, the authentication level for "I've done it" (a fresh passkey assertion with no SMS) is an AI proposal that has not been adopted.
