# Spine Pair Review — Nightshift

## Overall verdict
The pair is a usable contract. All five PRD journeys (verbatim names) plus Flow 6 and Flow 7 have a protagonist, numbered steps, a climax and a failure path. Every colour token has a hex value with a `-dark` twin and stated contrast. The 16 named components appear under identical names in both spines with real rules, and all 72 `{token}` references resolve. Nothing is critical. The gaps are at the edges: unnamed components that carry real screens (the B1 cluster card, timeline entries, links, console-sized buttons), a few statuses and states with no definition ("Waiting for later waves", "Out of date" listed as a repair status), open-item IDs that collide with surface IDs, and a lot of provenance narration that downstream readers do not need.

## 1. Flow coverage — adequate
Checked: UJ-1 to UJ-5 from `prd.md` §2 (names verbatim), Flow 6 and Flow 7 from the memlog, plus every FR with a user-facing surface (FR-5, FR-11 to FR-16, FR-19 to FR-24, FR-27/28, FR-32 to FR-34, FR-47, FR-50 to FR-52). All seven Key Flows name a protagonist, number their steps, mark a climax and give a failure path. UJ-4's "not applicable" is defensible.
### Findings
- **medium** UJ-1's severity is still undecided. The customer wireframe (B1, B2, B3, Slack) shows "Severity: Critical", and State Patterns maps Critical to a phone call, but UJ-1 step 2 sends a Slack alert. The memlog's last entry lists this as "Open for Amine", yet it is not in EXPERIENCE › Open items, so a mock or story built from the wireframe will show Critical plus a call (Key Flows › UJ-1 step 2; State Patterns › Severity). *Fix:* decide (Warning fits "alert when a decision is needed") and record it in UJ-1, or add it to Open items.
- **medium** There is no flow for the customer-performed manual repair or for hardware escalation (FR-20, FR-52: "the customer, or their hardware provider, for hardware and for the customer's own app"; Nightshift "prepares the evidence for the customer to send"). The only coverage is one sentence in Component Patterns › Manual-repair panel and a wireframe annotation next to B3-M after Approve. The evidence hand-off to a provider has no surface (Key Flows; IA › Customer view). *Fix:* add a variant to Flow 7 or a short Flow 8: the customer performs it or forwards the evidence, then presses **I've done it: check now**, then Nightshift checks.
- **medium** FR-19 (no tested repair: explain, state uncertainty, escalate, don't repair) has no flow and no B2/A2 variant. Both IA rows assume a proposed repair always exists (IA › A2, B2; State Patterns › Surface states). *Fix:* add a "No tested repair" state for A2/B2: what replaces the proposed-repair section, and who is told.

## 2. Token completeness — adequate
Checked: 68 colour tokens (34 light, each with a `-dark` twin, all valid 6-digit hex, all matching the Graphite Ledger block in `.working/color-themes-1.html`), 12 typography roles, 4 radii, 13 spacing tokens and 27 component entries. 62 references in DESIGN.md and 10 in EXPERIENCE.md all resolve. Contrast is stated for every neutral and every status ink-on-fill pair, light and dark.
### Findings
- **medium** Several component values are prose rather than tokens, so code that mirrors the spine has to parse them by hand: `'hatch 135deg {colors.stale-hatch-base} 5px / {colors.stale-hatch-stripe} 5px'` (chip-stale, stale-panel; 6px in attention-queue-row-stale), `severity-bar: '3px inset left, … by severity'`, `summary-tile.critical-variant: '… with … border'`, `health-grid-tile.no-open-problem: '… with 1px … outline'`, and `focus: '3px solid …, offset 2px'` (DESIGN.md frontmatter `components`). *Fix:* split them into structured sub-keys (`hatch-angle`, `hatch-stripe-width`, `base`, `stripe`; `bar-width`; `outline-width`, `outline-offset`) or give the literal CSS as the palette sheet does (`repeating-linear-gradient(135deg, … 0 5px, … 5px 10px)`).
- **medium** Contrast is not stated for `text-secondary` on tinted fills and on hatch, which are load-bearing pairs: the freshness line closes the Verified facts block, and stale customer cards read "Out of date · Last updated 02:10". Computed values: dark `#A3A9B3` on `stale-hatch-stripe-dark` `#3E4248` is **4.28:1, below 4.5:1**. Light on the stale stripe is 5.19:1. On success, explanation and critical fills it is 6.4–6.8 (light) and 5.5–6.5 (dark) (DESIGN.md › Colors; Components › Freshness line, Stale panel). *Fix:* say that text on a stale panel or card uses `neutral-ink` (5.6:1 dark), or adjust the dark stripe, and add the text-secondary-on-fill rows to the contrast table.

## 3. Component coverage — adequate
Checked: the 16 named components (Status chips, Verified facts block, Explanation block, Approval card, Manual-repair panel, Primary button, Secondary button, Attention-queue row, Summary tile, Health-grid tile, Freshness line, Stale panel, Info card, Check table, Progress steps, Settings row). Each has a DESIGN.md › Components entry and an EXPERIENCE.md › Component Patterns row with real rules, under identical names. Also swept both spines and both 2026-11-03 wireframes for UI elements that are used but have no name.
### Findings
- **high** The **cluster card** has no spec in either spine. It is the main element of B1 (one per cluster: severity, status, impact in words, freshness) and has its own states: current, "Out of date · Last updated 02:10", resolved, alert-only. The **timeline entry** that B4 Activity and the A2 Timeline are built from has no spec either; Progress steps covers only part of a B4 row (IA › B1, B2 "Reached from: Cluster card", B4; State Patterns › Freshness). *Fix:* add "Cluster card" and "Timeline entry" to DESIGN.md Components (tokens and prose) and EXPERIENCE.md Component Patterns (behaviour, states, click target).
- **medium** Links and text actions are not defined: "Review the proposed repair", "Review approval →", "Open in Quornex portal to review", "See full activity", "Ticked in your settings on 12 Oct", "Read the policy", "Dispute", "Revoke delegation", "Data leaving your cluster and management policy ›". The spines don't say which are buttons and which are links, or give a link colour or focus treatment. `primary` is reserved for the one decision per screen (DESIGN.md › Do's and Don'ts; EXPERIENCE.md › Interaction Primitives). *Fix:* add a `link` component (colour, underline, focus) and assign each of these labels to button-secondary or link.
- **medium** There are no console-sized buttons. `button-primary` and `button-secondary` hard-wire `{typography.customer-action}` (17px) and `{spacing.customer-tap-min}` (44px), but A3, A3-M and A4 also use **Approve this repair**, **Reject** and **Approve rollback for these 300 clusters** in the dense console (DESIGN.md frontmatter `button-*`; Layout & Spacing › Console). *Fix:* add a console size variant (console-chip or console-body type, compact padding).
- **medium** Interactive state appearance is missing beyond focus: hover and pressed for buttons, queue rows and tiles; the selected group in the A1 selector; disabled or read-only controls for "Not an administrator" (B6, B6b) and "Orvex support, not delegated" (A3, A3-M) (DESIGN.md › Components; EXPERIENCE.md › State Patterns › Surface states). *Fix:* add hover, pressed, selected and read-only tokens or rules. A disabled ink token would also cover read-only settings.
- **medium** The health-grid tile state "Heartbeat OK · Fleet reports not permitted: not included in fleet-wide correlation" is in EXPERIENCE.md › Component Patterns › Health-grid tile and in the A1 legend, but DESIGN.md `health-grid-tile` defines only critical, warning, no-open-problem and out-of-date. *Fix:* add its visual treatment (for example a no-open-problem tile with a marker and legend entry).
- **medium** Three A4 and A2/B2 elements have no component: the A4 wave progress (Step 3: "Wave 1 of 6 done…"), the A4 per-cluster table (permission, safety checks, repair status), and the **What Nightshift cannot see** block on A2 and B2. Because green means verified and yellow means explanation, a builder has to know this block is neither (IA › A2, A4, B2). *Fix:* name them. State that "What Nightshift cannot see" sits on a plain surface, and that the A4 table reuses Check table with a repair-status column.
- **low** The top navigation bar, the A5 dropdown filters, the A1 group selector, the health-grid legend and B1's compact "Needs your decision" card are named but have no visual spec beyond "compact version" (EXPERIENCE.md › IA; DESIGN.md › Components › Approval card). *Fix:* one line each, or point to the Quornex system once it is mapped.
- **low** Only `severity-chip` carries typography. The incident, repair and risk chip families and the base `chip-*` tokens have no type, padding or height, so console and customer chips may differ in size (DESIGN.md frontmatter). *Fix:* put typography and padding on the base `chip-*` tokens.

## 4. State coverage — adequate
Checked every IA surface (A1–A5, A3-M, Orvex support, Slack, B1–B6, B6b, onboarding, in-cluster dashboard) for empty, cold-load, focus, error, offline, permission-denied, stale and domain states. Coverage is broad but often marked [ASSUMPTION]: freshness, approval validity, withdrawn and re-issued requests, reject, alert-only, non-admin, decision not recorded, tick again and policy pending are all present.
### Findings
- **medium** "Waiting for later waves" (UJ-5 step 6; A4 wireframe) is used as a per-cluster repair status but is not among the State Patterns › Repair status values and has no chip mapping in DESIGN.md. *Fix:* define it as an A4-only rollout state with its chip (neutral or waiting), or add it to the repair status values.
- **medium** B3 and B3-M have no state for a request someone else has already answered (a delegate approved it, or another administrator rejected it) or for a signed-in person who may not approve (permission denied). Approver roles are [OPEN], but the screen state can be fixed now (State Patterns › Surface states; Open items A5). *Fix:* add "Already decided by <name> at <time>" (no buttons) and "You can't approve this request" (says who can).
- **low** Several empty states are missing: A5 when the filters match nothing, B4 with no activity yet, and B5 after a quiet night. The B5 wireframe shows "Nothing needs your decision right now." but no "nothing happened" summary (State Patterns › Surface states). *Fix:* add one line each.
- **low** Load and save failures outside decisions are not covered: settings changes failing to save (B6, B6b, onboarding), and the console or portal failing to load at all. That is different from one cluster being stale (State Patterns › Surface states, "Decision not recorded" covers decisions only). *Fix:* extend the "not recorded" rule to settings and add a page-level load error.
- **low** Two states are marked as not settled: "Request withdrawn" (wording not drafted) and "Manual repair, problem still there" (next step not recorded). Neither is in Open items, so it is unclear who closes them (State Patterns › Surface states). *Fix:* draft the wording or list both in Open items with an owner.
- **low** A3 has no state for two Orvex engineers deciding the same request at once (A3; Open items A5 "two different people"). *Fix:* reuse the "Already decided" state above.

## 5. Visual reference coverage — adequate
Checked: `imports/` is empty, and `mockups/` and `wireframes/` don't exist yet (mocks are pending and were ignored). `.working/` holds the two current wireframes (linked from DESIGN.md › Layout & Spacing by frame and from EXPERIENCE.md › Foundation), the palette sheet (linked from DESIGN.md › Colors, naming the Graphite Ledger block), the 2026-10-31 wireframes (declared superseded) and ia-proposal-v1/v2 (superseded drafts, rightly unlinked). - **low** Every visual link points into `.working/`. That is acceptable before Finalize, but the links and both frontmatter `sources` lists will break when the files are promoted (DESIGN.md banner, Colors, Layout; EXPERIENCE.md Foundation). *Fix:* when promoting to `wireframes/`, update the links and sources in both spines in the same edit.
- **low** EXPERIENCE.md's references are file-level only: the IA tables and Key Flows never point at a frame, while DESIGN.md › Layout does ("frame A1", "frames B3, B3-M") (EXPERIENCE.md › IA, Key Flows). *Fix:* add a frame reference per IA row (the surface IDs already match the frame titles).
- **low** Wireframe placeholder data contradicts the spine scenarios in ways a mock renderer will copy. A3-M uses shop-us-2 / C-0450 / 03:00–05:00 with the customer approving at 02:05, while Flow 7 uses shop-us-1 / 01:00–03:00 / 23:58. The customer wireframe header labels the memory-leak scenario "UJ-2" (it is UJ-1). The spines-win rule covers this, but the three mocks being rendered may inherit it. *Fix:* align the wireframe text with Flow 7 and UJ-1 when promoting.

## 6. Bloat & overspecification — adequate
Checked: pixel values against tokens, restatement of source material, prose against tables, and narrative not tied to a decision. DESIGN.md is tight, and its editorial voice in Brand & Style is appropriate. EXPERIENCE.md (~7,300 words, about three times the examples) is mostly load-bearing (exact labels, section orders, state wording) but carries noise.
### Findings
- **medium** Provenance and supersession narration runs through EXPERIENCE.md: "(Amine, 2026-11-03)", "accepted 2026-11-03", "superseded 2026-11-03", "as corrected the same day", "PRD change pending", dozens of times. Two rows of the Voice and Tone "Don't" column record withdrawn strings ("Expires at 02:44", "Heartbeat not permitted…") rather than anti-patterns a writer might reach for. This history belongs in the memlog (Foundation, Voice and Tone, State Patterns, Key Flows Flow 6 and Flow 7, Privacy). *Fix:* strip the attributions and keep each "Don't" only where it is a real temptation.
- **medium** The same rules are stated in several places, which invites drift. The Reject behaviour appears in Voice › Reject result, Interaction Primitives › Banned, Authorisation & approvals › Reject and Inspiration. The B3-M order appears in IA, Component Patterns › Manual-repair panel and Flow 7 step 2. Approval validity appears in State Patterns, Voice › After Approve and Open items A2. *Fix:* give each rule one home and cross-reference it from the others.
- **low** The Authorisation & approvals table and the Privacy & outbound channels table restate FR-21 and FR-6/PRIV-9 at length. The UX additions (queue labels, surfaces, "what No means" copy) earn their place; the restated rule text does not (EXPERIENCE.md › Authorisation & approvals, Privacy & outbound channels). *Fix:* cite the FR for the rule and keep only the UX layer.
- **low** The "Pending PRD changes" paragraph is a work queue for `bmad-prd`, not something a downstream consumer reads (EXPERIENCE.md › Open items, last paragraph). *Fix:* move it to `.working/open-items-2026-11-03.md` and the memlog.
- **low** DESIGN.md › Components prose repeats pixel values the tokens already carry ("4px left border", "3px left bar", "1.5px … outline", "3px … 2px offset"). *Fix:* reference the token, or accept it as readable restatement.

## 7. Inheritance discipline — adequate
Checked: all 9 `sources` paths resolve in both spines. UJ names are verbatim. Glossary terms (Orvex technical approval, agreed management policy, customer production, problem group, last-resort condition, expected interruption, alert-only, delegation, manual repair needed) match the PRD. Component names are identical across both files. All 10 EXPERIENCE.md token references resolve to DESIGN.md tokens by name.
### Findings
- **medium** Two ID schemes collide. Open items are numbered A1–A11 and B1, the same IDs as the surfaces A1–A5 and B1–B6. "[OPEN: architecture A6]" (Component Patterns › Explanation block) and "[OPEN: architecture A11]" (IA closure note) read like screen references, and "B1 Mapping neutral tokens" clashes with "B1 Home" (EXPERIENCE.md › Open items). *Fix:* renumber the open items (OI-1… or ARCH-1… / ORVEX-1) and update the inline references.
- **medium** DESIGN.md puts freshness inside the repair-status family. `repair-status-chip.out-of-date` and the prose list end with "Out of date (02:10)" (stale hatch). This contradicts EXPERIENCE.md's "four separate fields, never merged" and its repair status values; the queue shows "Out of date (02:10)" in the Updated column, not as a repair status (DESIGN.md frontmatter `repair-status-chip`, Components › Status chips). *Fix:* move it to a separate `freshness-chip` / `chip-stale` usage under Freshness.
- **low** The spines intentionally diverge from the current PRD: the heartbeat is required (PRD FR-6, PRIV-9 and NFR-4 still say optional, and addendum "For the UX" still lists the two dropped status texts); unanswered requests don't expire; FR-52 gets a time window; and onboarding defaults change. This is tracked, but an architecture reader taking PRD and spines together meets conflicting rules (EXPERIENCE.md › State Patterns › Freshness, Open items › Pending PRD changes). *Fix:* run the queued `bmad-prd` Update before architecture starts, or point architecture at the spine for these items.
- **low** Customer screens prefix "Severity:" and "Repair status:", but the spine gives no prefix for incident status. The wireframes show "Status: Waiting for customer" (Component Patterns › Status chips). *Fix:* name the customer label for incident status.
- **low** "Incident status" covers every problem (an informational disk cleanup included), while the PRD Glossary defines an *incident* as a user-facing disruption and a *problem* as any fault, failure or incident. The term is inherited from the PRD addendum, so this is noted rather than to be fixed here (State Patterns › Severity, statuses and risk). *Fix:* none needed now; flag it for the PRD glossary.
- **low** Weak citations. Freshness cites "(FR-4, FR-6)", but FR-4 is Nightshift's self-monitoring and the freshness rule is the pending FR-15 change. A2 cites "Danny, Exchange 5", but no Danny Q&A file is in `sources` (`.working/extract-challenge-danny.md` exists) (State Patterns › Freshness; IA › A2). *Fix:* cite the pending FR-15 change, and add the Danny extract to sources or drop the citation.
