## For the architecture

- **Independent self-monitoring (FR-4, Amine's idea):** a monitoring tool inside Nightshift that is independent of Prometheus, so that if Prometheus stops, Nightshift notices that metric collection has stopped (Amine, 2026-10-29).
- **Hosting provider:** the planning files say "a hosting provider"; the architecture is free to name the provider for the prototype (Amine, 2026-10-28).
- **Where Quornex Fleet runs (AI's reading, unconfirmed):** bare-metal servers under OMK, not hosted Kubernetes such as EKS. Basis: Danny names the launch hosting provider both in his bare-metal paragraph and as the place where Quornex Fleet runs (danny-qa Exchange 4).
- **Fleet learning pipeline (FR-37 to FR-40, unverified):** candidate design: sanitised evidence → a person diagnoses → rule and fix → replay test → shadow run across the fleet → gradual rollout with rollback → signed, versioned catalogue (AI's session-2 coaching feedback).
- **UX open items:** items O-1 to O-13 (`ux-designs/ux-nightshift-2026-10-31/EXPERIENCE.md`, Open items) are architecture- or Orvex-dependent details the UX kept open (Amine, 2026-11-03, UX work).
- **Revocation reaches the cluster:** answered. The cluster signs a receipt for every decision; until it arrives the person sees "Sent — not yet effective in the cluster", and stops are confirmed by a separate notice (FR-22; architecture AP-3, Amine, 2026-11-15). Was: how withdrawals, a switch to alert-only and unticks are delivered, confirmed and shown as "sent, not yet confirmed" (FR-22, D1; Amine, 2026-11-03, review of the update).
- **Undoing a rejection:** answered: 2 minutes, a starting value to test, timed by the cluster (FR-50; architecture AP-16, Amine, 2026-11-15). Was: the undo-rejection window length (Amine, 2026-11-03, review of the update).
- **In-cluster dashboard:** answered: a stable internal address, separate local passkeys, no per-repair approvals; withdrawals, rejections, unticks, alert-only and authorised settings changes, each with a receipt (PRIV-9; architecture AP-13, Amine, 2026-11-15). Still to verify per platform: DNS, certificates and routing (reachability on OMK is unknown). Was: withdrawals, the switch to alert-only and settings changes when the portal is off (Amine, 2026-11-03, review of the update).
- **Defined manual procedures for inconclusive checks:** which alternative evidence counts, and how each verified condition is recorded (FR-22, FR-52; Amine, 2026-11-03, review of the update).

## Input for the privacy and security review and the architecture

High findings from the second PRD validation (2026-10-31) that are design details rather than product requirements. They are handed to those deliverables instead of being added to the PRD (Amine, 2026-10-31). Full text: `history/reviews/review-after-security.md` (SEC-R2-*), `history/reviews/review-after-adversarial.md` (H-*) and `history/reviews/review-after-judge.md` (H*).

- **Approval surface:** render the action and target only from structured data, never from AI text; neutralise links and names an attacker controls; define approver roles, step-up authentication and how portal identities map to customers (in the first version, Slack is used only for notifications); require two different people where two approvals are needed (SEC-R2-03, SEC-R2-05, adversarial H-3). Step-up authentication: answered by the approval confirmation (passkey plus a one-time code by text message), pending feasibility and usability testing (FR-14; architecture AP-2, Amine, 2026-11-15).
- **Untrusted inputs beyond logs:** Kubernetes names and annotations, metrics, BMC strings, customer code and model output; define "independent signals" (SEC-R2-04).
- **Exfiltration and diagnostic access:** egress only through the gateway, except the three named paths with their purpose-specific controls (SEC-8, PRIV-4; architecture AP-8, Amine, 2026-11-15); define what "diagnostic access" to databases and Secrets allows (SEC-R2-06).
- **Code fixes:** pinning patch hashes, test-environment isolation (data, secrets, internet), engineer access as a channel, secret scanning before any hosted-model call, database migrations as prohibited actions, a review rule matching the two reviewers needed for catalogue entries, and keeping customer code out of fleet-wide entries (SEC-R2-07, SEC-R2-08, adversarial H-7, H-8, H-10). Secret scanning before a hosted-model call: answered (FR-43; architecture AP-6, Amine, 2026-11-15). Engineer access as a channel: still open (PRD Section 10, item 27).
- **Platform updates:** signing-key custody, who may label an update "routine", and protecting the enforcement code from being weakened by updates; version skew under customer-controlled updates (SEC-R2-09, adversarial H-11).
- **Hardware:** BMC credential custody at installation, role separation, risk levels for power actions, the BMC network as a pivot, and checking at installation that each BMC belongs to its node (SEC-R2-10, adversarial H-16). Risk levels for power actions: no hardware power actions in the first version; BMC access is read-only, and a BMC reading is used only when its system ID matches the node (SEC-3, FR-3; architecture AP-10, Amine, 2026-11-15).
- **Management agent:** its rights, and containment if it is compromised (SEC-R2-12).
- **Repairs adding up:** capacity-aware limits across different targets; FR-30's testability (adversarial H-4).
- **Stale monitoring:** pause automatic repairs while Nightshift's own data is stale (adversarial H-5).
- **Silent nodes:** fencing before stateful pods move off a node that may still be alive (adversarial H-6). Answered: only with a verified fencing and storage-safety procedure, otherwise a manual decision (FR-3; architecture AP-10, Amine, 2026-11-15).
- **Working without a model:** the core loop (detect, check, act, verify, record) works when no model is available (judge H6). This is now a PRD requirement for customers who have neither external-AI consent nor in-cluster AI (Section 7, "Without external AI"; 2026-11-02).
- **Cost and staffing:** human approval time is likely the dominant cost; count the review and approval work the PRD itself creates (judge H5, adversarial H-13).

## From the architecture reconciliation (2026-11-15)

Mechanism depth behind the PRD changes tagged "(architecture AP-n, Amine, 2026-11-15)"; the source is `architecture/architecture-nightshift-2026-11-03/ARCHITECTURE-SPINE.md`. Change report: `update-notes-2026-11-15.md`.

- **Approval confirmation (FR-14; AD-18):** the cluster stores only a keyed hash of the one-time code; the gateway polls quickly only while a confirmation is open, and this load is to be tested at 10,000 clusters; each cluster uses separately scoped SMS credentials where the provider supports it; Fleet monitors SMS use per cluster from the provider's own records, independently of the gateway.
- **Offline validity (FR-22; AD-24):** status confirmations carry an increasing signed sequence number; while disconnected, their age is measured with a local monotonic timer; confirmations dated ahead of the local clock by more than the allowed skew are refused, and a backward clock jump raises an alarm. Authenticated time is optional hardening to verify.
- **Probation rollback (FR-47; AD-45, AD-68):** the independent checker only reports health; a separate, narrowly authorised rollback guard can select only the pre-authorised recovery version. The checker and the guard are updated separately from routine releases.
- **Follow-up for the architecture documents** (done in the second pass of 2026-11-15; see `update-notes-2026-11-15.md`, "Second pass (remaining points)").
