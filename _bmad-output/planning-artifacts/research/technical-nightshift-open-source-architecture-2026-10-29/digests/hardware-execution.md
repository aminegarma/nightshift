# Hardware detection and bounded execution research

Access date: 2026-10-29. Scope: primary project repositories and official documentation retrieved during this run. Recommendations and sizing ranges below are engineering inferences, not benchmark results or adopted architecture decisions. Project constraints are requirements to evaluate, not external evidence. No release binaries were tested; default-branch documentation can describe unreleased behavior. Pin release, commit, image digest and dependency SBOM before adoption.

## Findings

Use distinct evidence, policy, approval and execution boundaries. A viable small local stack is node-problem-detector plus smartctl_exporter, a remote BMC exporter, and a narrowly scoped custom controller. Argo Workflows is a viable packaged execution alternative. Temporal and StackStorm warrant consideration for shared management-plane orchestration, but their persistence/services increase the cost of installing one complete stack per customer cluster. These are proposed fits inferred from the component descriptions below, not proof of safety or 10,000-cluster capacity.

Hardware failure detection must retain three separate perspectives: host logs/device telemetry, BMC management telemetry, and an observer outside the target cluster. An exporter being unreachable proves loss of observation, not a failed disk, failed power supply or permission to reboot.

## Node health and recovery choices

**Portable OSS detection:** Apache-2.0 [node-problem-detector](https://github.com/kubernetes/node-problem-detector) runs per node or standalone, reports Events/NodeConditions and optionally Prometheus metrics. It monitors logs, system stats, runtime/kubelet health, and custom plugins. Compile-time disabling can reduce its footprint. Its custom scripts must be packaged checks from the tested catalogue, never model-generated scripts. Host visibility and Kubernetes status writes are distinct privileges; losing API access must not erase locally buffered evidence. [README](https://raw.githubusercontent.com/kubernetes/node-problem-detector/master/README.md).

**EKS-native detection:** official [EKS node health documentation](https://docs.aws.amazon.com/eks/latest/userguide/node-health.html) describes Linux-only monitoring, enabled in Auto Mode, optional as add-on/Helm elsewhere, excluding Fargate. It surfaces hardware/runtime/kernel/network/storage conditions. This managed integration is an alternative to duplicate local detection on EKS, not the disconnected portable foundation. Kubernetes conditions/events and EKS observability expose evidence; retain Nightshift incident context across replacements. [AWS guide, node-health visibility section](https://docs.aws.amazon.com/pdfs/eks/latest/userguide/eks-ug.pdf).

**Medik8s NHC + SNR:** both Apache-2.0, repositories publish security policies. NHC evaluates conditions, creates templated remediation CRs and supports ordered remediators, minimum healthy or maximum unhealthy thresholds, and manual pausing. Automatic upgrade detection is documented only for OpenShift; generic Kubernetes requires an explicit maintenance integration. [NHC repository](https://github.com/medik8s/node-healthcheck-operator), [NHC README](https://raw.githubusercontent.com/medik8s/node-healthcheck-operator/main/README.md).

SNR reboots nodes using peer/API reachability decisions, with timeout-based safe-state assumptions for isolated nodes; it intentionally avoids reboot storms for API-server failure. This is not confirmation that a powered-off site can repair itself. [SNR behavior](https://www.medik8s.io/remediation/self-node-remediation/how-it-works/). Its documented limitations include at least two workers for fencing, no IPv6, one health detection system at a time, privileged namespace requirement and a common timeout sized for the longest watchdog timeout. Validate against the chosen release; this documentation includes historical upgrade notes. [Known issues](https://www.medik8s.io/remediation/self-node-remediation/known-issues/). Fence Agents Remediation documents reboot-only support and requires pod-to-management-interface connectivity. [FAR limitations](https://www.medik8s.io/remediation/fence-agents-remediation/limitations/).

**EKS-native repair alternative:** [AWS repair documentation](https://docs.aws.amazon.com/eks/latest/userguide/node-repair.html) permits managed-node-group parallelism, unhealthy limits, condition/reason overrides and NoAction; Auto Mode repair is always enabled and not configurable. Default repair does not address DiskPressure or MemoryPressure. Assign a single repair owner per node pool: Nightshift should observe/provider-delegate where AWS owns repair, or explicitly configured local execution where the operator owns it. Avoid NHC/Nightshift/provider racing on the same node. Replacement/reboot must not be equated with database recovery or application consistency.

None of these engines by itself enforces “no customer database/data deletion.” Proposed enforceable contract: typed action identifier + catalogue revision + target UID/provider instance identity + bounded parameters; signed separate approval binding this exact action/target/evidence digest and expiry; executor rechecks preconditions, lease, maintenance window and concurrency budget immediately before mutation. No arbitrary command field. Deny customer database APIs, SQL, storage/PVC deletion, wipe/format, arbitrary filesystem deletion and generic shells. Administrative Kubernetes node-object deletion, if ever supported, requires a separate approved action and fencing proof; deleting a Node object does not stop its workloads. Treat reboot/replacement with stateful/local-storage workloads as unsafe until workload policy and recovery checks pass. These are recommended Nightshift controls, not built-in guarantees from the evaluated products.

## Independent watchdog and full-site outage

Two OSS options are (1) [Healthchecks](https://github.com/healthchecks/healthchecks), BSD-3-Clause, self-hosted missed-heartbeat detector with configurable grace and notification integrations, Python/Django + database; (2) [Prometheus blackbox_exporter](https://github.com/prometheus/blackbox_exporter), Apache-2.0, HTTP/HTTPS/DNS/TCP/ICMP/gRPC probes, TLS/basic authentication and documented security policy, combined with independently hosted alert evaluation. First detects absent push heartbeats; second actively checks reachability. Neither proves the power-loss cause by itself.

Inference: place watchdog, alert transport and any recovery coordinator outside the target cluster **and its power/network failure domain**. A separate pod in the same cluster or a BMC on the same dead power feed is insufficient. Disconnected operation can use a separately powered local management appliance/UPS and private notification route; complete site power/network loss needs an off-site observer or physically independent channel. Loss of heartbeat may justify escalation and bounded diagnostics, never unconditional mass reboot. Recovery still requires reachable, powered management hardware and separately approved catalogue actions.

## Sizing and scale uncertainty

No retrieved source benchmarks these candidates for Nightshift or proves 10,000-cluster operation. Except StackStorm's cited minimum, the following are **initial benchmark envelopes**, not claims: each exporter/NPD 25–150 MiB and 5–100 millicores idle-to-modest polling; custom local controller 64–256 MiB and 10–100 millicores with tightly scoped caches; Argo controller/server together 256 MiB–1 GiB idle/modest concurrency plus action pods; Scrutiny hub with InfluxDB 0.5–2 GiB plus retention disk; Healthchecks service/database 0.5–2 GiB; shared production Temporal 2–8 GiB across services plus durable database/visibility capacity. Larger inventories, timeouts and retained histories can exceed all ranges. Benchmark hardware/BMC scrape latency, privileged collection, pod churn, queue backlog, retention, and disconnected replay before committing limits.

At 10,000 clusters, even 100 MiB baseline per local component is about 0.95 TiB fleet memory; 10 millicores is 100 cores. Favor existing local telemetry, bounded collectors, staggered scrapes, admission limits and tenant-sharded management services. Benchmark per-node as well as per-cluster multiplication. Fleet-wide alert storms require per-site action budgets and a global stop policy; communication loss must leave a locally enforceable, expiring authorization boundary.
