# OSS observability evidence digest

Accessed: **2026-10-29 UTC**. Scope: official documentation and upstream GitHub retrieved during this run. Local autonomy, local raw-log privacy, and a possible 10,000-cluster fleet are evaluation constraints supplied by the project, not externally established facts. Recommendations below are engineering inferences, not benchmark results or final architecture decisions.

## Candidate comparison

| Layer | Retrieved evidence | Nightshift implication (inference) |
|---|---|---|
| Prometheus | Apache-2.0 upstream. Local TSDB supports WAL and retention limits; it is neither clustered nor replicated. Documentation gives a rough 1–2 bytes/sample average, excluding the need to budget WAL/head/compaction space. [Repository](https://github.com/prometheus/prometheus), [storage](https://prometheus.io/docs/prometheus/latest/storage/). | Strong baseline for independent local scraping, rules, and short retention. A central remote backend must not become a dependency of local detection. HA needs separate replicas and failure testing. |
| VictoriaMetrics OSS | Single-node and cluster editions are Apache-2.0; enterprise is separately identified. MetricsQL is PromQL-like, not a guarantee of identical semantics. Vendor resource-saving claims are not independent Nightshift measurements. [Official documentation](https://docs.victoriametrics.com/victoriametrics/). | Benchmark single-node against Prometheus using the actual rule corpus, churn and recovery scenarios. Do not assume enterprise downsampling/retention features belong to OSS. Potential fleet backend, but 10,000-cluster capacity remains unverified. |
| OTel Collector | Apache-2.0 core; agent and gateway patterns are documented. Export queues/retries and persistent storage mitigate loss but do not eliminate it; the resilience guide documents default retry expiry and overflow/crash loss scenarios. [Repository](https://github.com/open-telemetry/opentelemetry-collector), [deployment](https://opentelemetry.io/docs/collector/deploy/), [resilience](https://opentelemetry.io/docs/collector/resiliency/). | Prefer where OTLP and cross-signal processing are requirements. Pin a minimal component distribution and validate each receiver/processor/exporter separately; core license or maturity does not establish every contrib component's readiness. |
| Fluent Bit | Apache-2.0. Its buffering guide describes memory and filesystem modes; filesystem persistence trades overhead for reduced loss, and corruption can cause chunk discard. [Repository](https://github.com/fluent/fluent-bit), [buffering](https://docs.fluentbit.io/manual/data-pipeline/buffering.md). | Candidate for a bounded local log pipeline. Configure limits and observable loss explicitly; do not infer losslessness from disk buffering. No comparative RAM benchmark was established here. |
| Vector | Upstream reports MPL-2.0 plus additional license files. Disk buffers persist across restart; documentation specifies ~256 MiB minimum per disk buffer, periodic sync, and exit on unrecoverable I/O errors. Overflow buffer topology is explicitly not production-ready. [Repository](https://github.com/vectordotdev/vector), [buffering](https://vector.dev/docs/architecture/buffering-model/). | Candidate when transformations justify it. Budget each sink's buffer and avoid experimental overflow topology. Check packaged dependency notices and obligations before redistribution. |
| Loki OSS | AGPL-3.0 upstream. It indexes stream labels rather than log bodies and stores compressed chunks; filesystem storage is described for development/proof of concept. [Repository](https://github.com/grafana/loki), [overview](https://grafana.com/docs/loki/latest/get-started/overview/). | Favor evaluation for operational stream/time queries with bounded labels. Production local storage needs a deliberate supported storage plan, retention and recovery test. Vendor scale language does not establish Nightshift fleet readiness. |
| OpenSearch OSS | Apache-2.0 upstream search engine. Production guide requires replacing demo credentials/certificates, setting authentication/roles, multiple nodes and snapshots; recommends local SSD rather than network filesystems. [Repository](https://github.com/opensearch-project/OpenSearch), [production installation](https://docs.opensearch.org/latest/install-and-configure/install-opensearch/index/). | Candidate when indexed search requirements justify its operational footprint. A replicated search cluster per customer cluster is a substantial fleet cost hypothesis, not a measured cost result. Amazon OpenSearch Service is not the OSS edition evaluated here. |

## Complementary detection, probes and privacy

- **node_exporter, kube-state-metrics and node-problem-detector serve different roles.** node_exporter exposes machine metrics and its container example requires host namespace/filesystem access; kube-state-metrics exposes Kubernetes object state; NPD turns node problems into Events/NodeConditions and can export local Prometheus metrics. All three upstream repositories identify Apache-2.0. They complement rather than substitute for one another. [node_exporter](https://github.com/prometheus/node_exporter), [kube-state-metrics](https://github.com/kubernetes/kube-state-metrics), [NPD](https://github.com/kubernetes/node-problem-detector). Keep collector permissions narrow and treat host mounts and Kubernetes write permissions as separate attack surfaces (inference).
- **Blackbox and prediction are signals, not authorization.** The upstream blackbox exporter provides a probing component; deploy probes on both sides of relevant failure boundaries (inference). Prometheus `predict_linear` performs simple regression, requires at least two float samples and is intended only for gauges. A disk-exhaustion forecast should be guarded by freshness, sustained trend and actual free-space thresholds before any remediation (inference). [Exporter](https://github.com/prometheus/blackbox_exporter), [function definition](https://prometheus.io/docs/prometheus/latest/querying/functions/#predict_linear).
- **External watchdog:** Healthchecks is BSD-3-Clause and alerts when scheduled pings fail to arrive. A separately hosted instance can receive only opaque cluster IDs, timestamps and status, avoiding raw-log export (design inference). It must live outside the monitored failure domain; heartbeat absence cannot distinguish network partition from controller failure. Its documented application stack includes a database, so self-hosting also needs maintenance and backup. [Upstream](https://github.com/healthchecks/healthchecks).
- **Local raw logs:** none of these product names enforces locality. Keep receivers, queues, storage, backups and query access inside the customer's approved boundary; export allowlisted aggregate evidence only (proposed design). Redaction must precede any external exporter, and tests must inspect queued records, errors and retry paths, not merely successful payloads.
- **Loki security:** its guide requires an authentication layer, discusses proxy-populated tenant headers and documents native transport mTLS. Tenant headers alone are not identity. [Authentication](https://grafana.com/docs/loki/latest/operations/authentication/). No current-CVE clearance was performed for any candidate; release activity is not security assurance.

## EKS scope limits

AWS states Fargate does not support DaemonSets, privileged containers, HostPort or HostNetwork. Therefore a standard host exporter/NPD/node log DaemonSet cannot be promised for Fargate; sidecar or managed telemetry alternatives need a separate capability matrix. This is a documented platform limit, not a product defect. [Fargate considerations](https://docs.aws.amazon.com/eks/latest/userguide/fargate.html).

EKS control-plane logs are supplied through CloudWatch, are best effort, disabled by default and incur ingestion/storage charges. An in-cluster log agent cannot be presented as equivalent coverage. Strict raw-log locality must explicitly define whether customer-account CloudWatch is an allowed boundary; otherwise those control-plane logs are unavailable under the proposed rule. [Control-plane logging](https://docs.aws.amazon.com/eks/latest/userguide/control-plane-logs.html).

## Cost model and validation gates

**Illustrative arithmetic, not measured sizing:** 100,000 active series scraped every 30 seconds yield approximately 3,333 samples/s. At the Prometheus documentation's rough 1–2 bytes/sample, seven days of sample storage is about 2–4 GB per cluster before index/head/WAL/compaction, replica, backup and filesystem overhead. Ten thousand such clusters produce about 33.3 million samples/s and 20–40 TB of seven-day sample data before those overheads. This shows why cardinality and retention contracts matter; it does not size a fleet backend. [Storage formula](https://prometheus.io/docs/prometheus/latest/storage/).

**Illustrative fleet sensitivity:** an additional reserved 256 MiB per cluster multiplies to ~2.44 TiB over 10,000 clusters; an additional 0.1 CPU per cluster multiplies to 1,000 CPUs. These are assumed reservations, not candidate resource claims. Raw logs at an assumed 1 GB/day per cluster and seven days imply 70 TB uncompressed fleet retention before indexes, replication or compression. No dollar figure is justified without customer placement, node counts, ingest/query load, storage class, utilization and egress prices.

Before selecting defaults, measure idle and p95 CPU/RSS, active-series churn, scrape/rule latency, API-server watch load, local log burst behavior, queue saturation, disk-full/crash recovery, restart catch-up, redaction escapes, and seven-day disconnection. Test in EC2-backed EKS and record Fargate exclusions. Require local alerts and approved autonomous actions to continue while the fleet service is unavailable. **No retrieved source establishes this exact architecture at 10,000 clusters, and no production performance or comparative resource claim is verified by this digest.**
