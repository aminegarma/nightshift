## Design findings to resolve

1. **Medium — external-watchdog arrow bypasses the drawn egress verifier.** Section 5 draws `CHECK --> WATCH`, whereas the stated primary boundary is positive-schema validation for outbound data. A heartbeat can be a separate minimal approved schema, but that is not explicit in the diagram. Route through an approved heartbeat validator or label the path as a strictly bounded authenticated heartbeat with no error text/raw evidence. Otherwise an implementation could leak diagnostic details through heartbeat metadata despite conforming to the picture.
2. **Low — hosted return path and local return path are asymmetric.** `EV --> FACT --> HOSTED` and `HOSTED --> AI` express a valid sanitized request/untrusted response split. This is not an outbound-response privacy violation: response data is inbound. However, `AI --> LOCAL` omits its return edge, and the diagram does not show how an investigation requests another fixed query. Clarify these logical interfaces before implementation so a generic tool-call loop is not inferred. The prose already prohibits arbitrary operations.
3. **Medium implementation gate — inference endpoint authentication needs a complete surface.** Section 8 calls for authenticated APIs, but vLLM's current [security page](https://docs.vllm.ai/en/latest/usage/security/) documents that its API-key option protects selected path prefixes while other inference/operational routes remain unprotected. “Set API key” alone would not implement the report's intent. Require a network boundary and gateway allowlist/authentication covering every exposed route; this is a missing implementation detail, not evidence the proposed design is already unsafe.
4. **Low — release arrow could be mistaken for a repair action.** `FLUX --> PROPOSE` visually feeds release delivery into the live repair request. The caption correctly says releases change catalogue/software state rather than initiating individual repairs. Model catalogue state separately during architecture work to remove this visual contradiction. No report text authorizes GitOps to submit repairs.

## Estimates and unverified assertions

Section 9's CPU/RAM envelopes, prices, incident counts and GPU examples are explicitly estimates/scenarios, not upstream requirements or observed measurements. They remain unsourced estimates and must not be promoted into deployment requests, minimum hardware or pricing claims. Simple arithmetic is coherent to the stated rounding: base three-node CPU about 0.5–2.6 cores and RAM about 1.4–5.1 GiB; 1 KiB/minute across 10,000 clusters about 14.7 GB/day decimal; seven days at 1 GB/day across the fleet 70 TB decimal. The report correctly excludes index/WAL/replica overhead from compressed sample arithmetic and does not claim verified fleet capacity.

The six-source check did not independently verify the separate Prometheus storage byte/sample estimate, all licensing/release claims, hardware behavior, or approval semantics. The custom controller, sanitization boundary, offline expiry, fencing and exact-once logical behavior remain proposals requiring the documented PoCs. The report appropriately identifies uncertainty and does not establish those guarantees from dependency maturity.
